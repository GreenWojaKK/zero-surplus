# 구현 상태와 남은 일

[아키텍처](../docs-translate/ko/architecture.md)

## 현재 상태

`zero-surplus` 0.1.0은 용량 측정·비교, 실행 기록 조회, 폴더별 마지막 사용, Python 환경의 사용 프로젝트 확인, 경로 감시, 진단 자료 내보내기를 구현한다. 지금 남은 구현 작업은 프로젝트 설정 판독 실패를 `refs` 결과에 드러내는 것이다. 코드 버전과 의존성은 [Cargo.toml](../Cargo.toml), [Cargo.lock](../Cargo.lock)을 기준으로 한다.

## 확인된 문제

### 설정 판독 실패에 따른 환경 오분류

- **확인 방법** — 실행 재현.
- **발생 조건** — 프로젝트의 `.vscode/settings.json`이 파싱되지 않는 경우.
- **관측 결과** — 환경 경로를 지정한 정상 설정에서는 정리 후보가 0개였다. 같은 파일을 불완전한 JSON으로 바꾸면 후보가 1개로 늘었다. 결과의 `scope.unreadable`과 `unresolved_references`는 모두 비어 있고 종료 코드는 0이었다.
- **원인** — `jsonc()`가 읽기·파싱 오류를 `None`으로 바꾸고, `read_project()`가 빈 참조 목록을 정상 반환한다. 후보 선정은 참조 목록이 비었는지를 사용한다.
- **영향** — 설정을 읽는 데 실패한 환경이 사용처를 찾지 못한 환경으로 분류된다. Python 환경은 설정으로 다시 만들 수 있어 다른 작업보다 뒤에 둔다.

재현에는 프로젝트 폴더와 환경을 대신하는 빈 디렉터리를 준비하고, 정상 설정의 `python.defaultInterpreterPath`가 그 디렉터리 아래 `python.exe`를 가리키게 한다. 다음 명령을 실행한 뒤 설정 내용을 `{"python.defaultInterpreterPath":`로 바꾸고 같은 명령을 다시 실행한다.

```text
zero-surplus refs --project <프로젝트> --env <환경 디렉터리> --no-activity
```

관련 구현은 [프로젝트 설정 판독](../src/refs/projects.rs)의 `jsonc()`·`read_project()`와 [환경 분류](../src/refs/mod.rs)의 `unreferenced` 구성 부분이다.

## 판독기 대조

한 PC에서 수집한 사본(`collect` 결과 `src-20261119T174955Z-7144`)을 두 도구로 읽어 비교했다. Prefetch 파일 435개(형식 버전 31, 모두 MAM 압축)와 SRUM DB 사본(SHA-256 `DCB0B4D1…2EA276`, Clean Shutdown)이다. 참조 도구는 PECmd 2026.10.3과 SrumECmd 2026.10.1이고, SrumECmd에는 같은 DB의 별도 복사본을 주었다.

| 출처 | 비교한 것 | 결과 |
|---|---|---|
| Prefetch | 435개 파일 전부의 실행 파일 이름, 실행 횟수, 실행 시각 8개, 실행 파일 경로, 참조 파일 목록 | 2개 파일의 참조 파일 목록을 빼고 모두 일치 |
| SRUM | SrumECmd가 앱 1,297개로 묶은 기록 중 표본 28개. 앱 자원 사용 기록 수와 네트워크 기록 수, 전·후경 CPU cycle, 전·후경 디스크 읽기·쓰기 바이트, 네트워크 송·수신 바이트, 첫 기록과 마지막 기록 시각(12개 항목) | 비교한 27개 앱의 모든 항목 일치. 1개는 비교할 수 없음 |

SRUM 표본은 앱 자원 사용 기록이 많은 15개, 네트워크 기록이 많은 10개, `python.exe`·`claude.exe`·`codex.exe`·패키지 앱 하나다. 장치 경로, `svchost.exe [netsvcs]` 같은 서비스 호스트, 서비스 이름, 패키지 이름 형태의 식별자가 모두 들어 있다.

차이와 원인은 다음과 같다.

- **실행 시각의 순서.** 12개 파일은 파일 안의 실행 시각 칸이 시간순이 아니다. 몇 초 안에 여러 번 실행된 프로그램이다. PECmd는 칸 순서대로 `LastRun`, `PreviousRun0…6`에 싣고 zero-surplus는 최신순으로 정렬한다. 값의 집합과 가장 최근 시각은 435개 모두 같다.
- **참조 파일 목록 2건(`PHOTOS.EXE-B6F10F7E.pf`, `PHOTOS.EXE-DBBC9D8A.pf`).** 파일 이름에 `, `가 든 항목이 있다. PECmd는 목록을 `, `로 이어 출력하므로 그 이름이 세 조각으로 나뉜다. zero-surplus는 이름 하나로 낸다.
- **실행 파일 경로.** PECmd는 실행 파일 이름과 같은 참조 파일을 모두 `FullPath`에 쉼표로 잇는다. zero-surplus는 후보가 하나면 그 경로를, 여럿이면 파일 이름의 해시로 고른 하나를, 고를 수 없으면 후보 목록을 낸다. 후보가 여럿인 19개 중 8개를 해시로 골랐고 11개는 후보 목록으로 남는다.
- **파일 이름의 해시.** 후보가 하나인 377개 중 188개가 장치 경로의 해시와 맞는다. 나머지는 실행 인자까지 해시에 넣는 프로그램(서비스 호스트, 패키지 앱, 다중 프로세스 앱)이라, 해시는 후보가 여럿일 때 고르는 데만 쓴다.
- **SRUM에서 비교할 수 없는 1개.** `AppId` 1은 `SruDbIdMapTable`에 이름이 없다(네트워크 기록 1,270건). zero-surplus는 이름이나 경로로 조회하므로 이 기록은 어느 조회에도 나오지 않는다.

비교하지 않은 것은 다음과 같다.

| 항목 | 이유 |
|---|---|
| Prefetch의 볼륨 정보와 디렉터리 목록 | zero-surplus가 출력하지 않는다. 볼륨 일련번호는 참조 파일 경로를 드라이브 문자로 바꾸는 데만 쓴다. |
| Prefetch 형식 버전 31 외의 파일 | 대조한 PC에 없다. |
| SRUM 표본 밖의 앱 약 1,270개 | 앱마다 CLI를 한 번 실행하는 방식이라 표본으로 비교했다. |
| SRUM의 날짜별 합계와 사용자 SID | 날짜별 합계는 같은 기록을 지역 시각의 날짜로 나눈 값이다. 사용자 SID는 비교 대상에 넣지 않았다. |
| SRUM의 수명이 짧은 앱 항목(`!!이름!시각!번호!`) | 표본에 없었다. |
| UserAssist와 ShellBags | 참조 도구 범위 밖이다. UserAssist 레코드 수는 PowerShell 집계와 맞는 것을 확인했다. |

## 남은 검증

- 취소 테스트는 `ZERO_SURPLUS_TEST_ABORT_BEFORE_COMMIT` 훅으로 저장 직전 종료를 재현한다. 실제 콘솔 중단 신호와 순회 종료까지의 동작은 별도로 검증한다.
- 감시의 알림 버퍼 초과, `collect`의 SRUM 재시도가 끝까지 실패하는 경로를 테스트에 추가한다.
- Claude Code의 `bin/`이 PATH에 올라갈 때 `zero-surplus.exe`가 이름만으로 실행되는지, Codex가 루트 `plugin.json`과 `.agents/plugins/marketplace.json`의 `./` 경로로 플러그인을 찾는지 GitHub에 올린 뒤 확인한다.

## 성능 검증 작업

`scan`은 파일·폴더 수, 경과 시간, 최대 메모리, 스레드 수를 `stats`에 저장한다. 다음 성능 비교에서는 재생성 가능한 디렉터리 구조를 사용하고 파일 수·깊이·크기 분포와 빌드 조건을 기록한다. 같은 입력에서 스레드 수를 바꾸며 합계의 일치, 경과 시간, 최대 메모리를 비교한다. 배포 바이너리, 빌드 산출물, 저장된 조사 결과의 크기도 각각 측정한다.
